# Sessions and results

Read the assigned node packet and only the resources needed for that task. The Host owns routing, input projection and mechanical checks; ordinary progress/authority lookup is not a request to inspect the full Workflow or audit every resource.

- Start with `caw run` using the selected Workflow, absolute workspace and declared inputs. Resolve reported dependency requirements before execution.
- Provider nodes use focused child sessions. Thread `start` creates a persistent session; `continue` follows its declared upstream session and Provider. Keep that lineage when resuming.
- Main `worker` uses isolated context. Main `orchestration` uses the original chat and native tools under Cooperative policy. Use the grants returned by `main_task`; helpers remain within that grant and finish before Main completion.
- The Run workspace may differ from the original chat cwd. Use `main_task.workspace` and its write grant for task paths; do not ask the user to move chats or split an unused branch. An explicit Run `main_modes` worker selection also applies to declared current-Main acceptance, with actual worker identity recorded separately from the initiating Main owner.
- Read large inputs through their declared resource interfaces. Bind unchanged records and file references directly between nodes.
- For `pi_caw_material` values, read the complete pinned resource with `read_workflow_resource_chunk`, following `next_byte` until `complete`, then decode its declared encoding. For program `output_ref`, use `read_program_output` for exact stdout/stderr chunks; a preview is not the complete log.
- Write only assigned artifacts and submit new semantic values through `caw_submit_result`. For current-chat Main, submit through `caw main_result` and finish the turn.
- For `result_mode: per_item`, repair only unresolved items in the same child session. With `item_delivery: incremental`, wait for acceptance before releasing the next item. Retain accepted items.
- Use Host notifications or `caw wait` for progress. For interrupted dispatch or uncertain shutdown, follow [recovery](recovery.md) before retrying.
- Run listing and `inspect_run` observe the committed journal without joining writer admission. For an orphan admission record, use `inspect_run_admission` for the exact Run, then pass only selected returned `records` to `recover_run_admission`. Both operations require the original current chat; only recovery requires explicit human confirmation (or the authenticated human Workbench API). Tool arguments cannot grant human authority. Inspection exposes PID, creation time, relative locator, byte hash and physical identity, excluding owner/controller tokens. Recovery retires only unchanged records whose owners are confirmed absent, retaining private evidence. It does not repair a torn journal, change business state, adopt a controller, retry uncertain effects or start a driver. Active, unverified, changed and corrupt records stay protected. History maintenance preserves Runs with pending admission ownership.
- Empty queue retirement containers are informational. Retained `record.json` proof is inspectable and protected, not a pending-owner deletion target. Existing legacy `.recovery.lock` ownership is reported as `recovery_pending`; this operation cannot clear an ownerless legacy recovery marker. A partially completed history trim is recoverable only while its original strict journal, pins and controller remain available. If a batch fails after retiring some records, error details include their retained evidence and the failed locator; inspect the remaining ownership before continuing.
